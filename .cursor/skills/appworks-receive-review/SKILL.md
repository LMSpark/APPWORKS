# 接收评审意见

先核实，再实施。技术正确优先于附和。

## 处理顺序

1. **读完整**：读完全部意见再反应。
2. **复述**：用自己的话复述每条要求；说不清的先问。
3. **核实**：对照真实代码，检查这条意见在本仓是否成立：会不会破坏现有功能？当前实现有没有历史原因？评审者是否缺少上下文？
4. **评估**：技术上对本仓合理吗？
5. **回应**：陈述技术事实的认可，或带理由的反驳。
6. **实施**：一次一条，每条改完立即做最小验证。

## 不清楚就停

意见中任何一条不清楚，**先不实施任何一条**（条目之间常有关联），整体澄清后再动手。

示例：
- 意见 1-6，我理解 1、2、3、6，不清楚 4、5。
- 错误：先做 1、2、3、6，之后再问 4、5。
- 正确："1、2、3、6 已理解；4、5 需要澄清后再一起处理。"

## 本仓特有的关卡

- **范围关卡**：采纳意见需要改的文件、公共 API、依赖或数据结构超出已批准方案（`notes/plan-*`）时，**不得直接实施**。按根 `AGENTS.md` 视为超范围变更，停下回报，回到阶段 2 或阶段 4。
- **YAGNI 检查**：评审建议"做得更完整"时，先 `rg` 查实际使用方。没有调用方就问"要不要删掉，而不是扩展"。
- **规范优先**：与根 `AGENTS.md` 或 `ai-coding-kit` 硬门禁冲突的建议，说明冲突并拒绝，不执行。
- **不 commit、不 push**：改完不自动提交。

## 外部评审者的意见

实施前检查：技术上对本仓成立吗？会破坏现有行为吗？当前实现为什么是这样？评审者了解完整上下文吗？

- 建议看起来不对：用技术理由反驳，引用可运行的测试或代码。
- 无法核实：直接说"没有 X 我无法验证，要调查、询问还是按建议做？"。
- 与用户此前的决定冲突：先和用户讨论，不自行裁决。

## 实施顺序

多条意见时：先澄清 → 阻断性问题（破坏、安全）→ 简单修复 → 复杂修复。每条单独验证，最后确认无回归。验证的收尾声明遵循 `appworks-verify-before-claim`。

## 回应方式

正确的意见：直接说"已修复，改了 X"，或只让代码说话。不要写"你说得对！""好观点！""谢谢指出"。

自己反驳错了：事实性更正，"我核实了 X，它确实是 Y，原判断有误，现在修复"。不长篇道歉，不为之前的反驳辩解。
