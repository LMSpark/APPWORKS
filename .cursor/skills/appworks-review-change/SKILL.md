# 审查 AppWorks 变更（只读）

对照已批准意图和当前仓库事实审查交付行为。发现项优先，过程叙述和个人偏好不得稀释正确性风险。

## 边界

- 只读：不编辑、不暂存、不提交，不把审查变成未经批准的修复。
- 不批准方案；审查结论不是用户审核，不能授权实施。
- 不代替验证：不得编造"验证通过"。验证缺失时，指出哪些完成声明缺乏证据。
- 不报风格、命名、格式偏好，除非造成真实契约或维护缺陷。
- 没有可达路径和直接证据的假设，不报。

## 流程

1. **建立审查基线**：读 `notes/plan-*` 中对应方案（目标、影响范围、验证计划）、`git status` 与 `git diff`，以及验证结果。方案缺失时向用户要，不要猜意图。
2. **完整阅读**每个变更文件，再追踪调用方、消费者、包导出、测试、配置、生成物（`generated/`）和运行时边界。按 `knowledge/README.md` 决策表读相关知识文件。
3. **对照方案**：检查实际改动是否超出方案列出的影响范围；超出的文件本身就是发现项。
4. **按优先级找缺陷**（见下）。
5. **输出报告**。

## 找什么（按优先级）

1. 行为与需求或已确认不变量相矛盾；
2. 权限、敏感数据、副作用被绕过；
3. 绕过模型层：直接写页面四文件、绕过 `ProjectModel` / ClassModel 工具、绕过 dirty 与显式保存链路；
4. 依赖方向或公共出口违规（包间依赖、`export *` 的公共 barrel、深层 import）；
5. 公共 API 变更未同步消费者、包导出配置、路径别名；
6. 回归、不安全的兼容行为、静默兜底掩盖缺失 API 或非法配置（根 `AGENTS.md` 2.11 要求 fail-fast）；
7. 违反根 `AGENTS.md` 第 2 章硬门禁并有实际后果：interface 大平层、矩阵式命名、目录文件数超 10、参数超 3 个、`as` 类型断言等；
8. 验证缺口导致完成声明不成立（缺负向测试、受影响消费者无证据）。

## 发现项门槛

一条发现必须同时有：可达行为或被违反的契约、`文件:行` 位置、直接证据、最小修正方向。宁可一条强发现，不要多条推测变体。

| 优先级 | 含义 |
| --- | --- |
| P0 | 严重安全、数据丢失或产品不可用 |
| P1 | 核心路径上高概率的正确性或安全缺陷 |
| P2 | 交付前应修复的有界行为/兼容缺陷 |
| P3 | 真实但低影响的缺陷或证据缺口 |

类别：`business-correctness`、`security-permission`、`model-bypass`、`dependency-boundary`、`public-api-consumer`、`regression`、`testing`。

## 方案沉默与搁置项

- **方案没写的情形不等于允许**：对方案和需求没覆盖的输入或状态，按"一个合理的使用者会期望什么"判断；若此时行为会让使用者受损，就是发现项。分级看对使用者的实际影响，不看方案是否提到触发条件。
- **搁置项必须列出**：审查中考虑过但判断"超出方案范围、不作为发现项"的行为，逐条写一行并给出理由。由用户或实施者逐条裁决，不得静默丢弃。没有则写"无"。

## 输出

```markdown
## 审查报告
- 审查对象：方案文件 / diff 范围 / 验证结果引用
- 发现项（按 P0→P3）：
  1. [P?][类别] 标题 — 文件:行 — 触发路径 — 证据 — 最小修正方向
- 搁置项：考虑过但判断不在方案范围内的行为 + 理由（无则写"无"）
- 方案偏差：超出影响范围的文件（无则写"无"）
- 验证缺口：哪些完成声明缺证据（无则写"无"）
- 待沉淀知识候选：仅列出，用户确认前不写入 knowledge/
- 结论：存在可行动发现 / 无可行动发现（noActionableFindings）
```

无发现时直接写"无可行动发现"，不要凑数。可复用的非显而易见发现只作为候选列出，由根 `AGENTS.md` 阶段 7 询问用户后再写入 `knowledge/`。
