# 先验证，再宣称

**没有刚刚运行的验证证据，就不能声称完成。** 违反字面等于违反精神。本规则落实根 `AGENTS.md`"未完成验证计划前，禁止宣称已完成/可交付/可提交"。

## 门禁

宣称任何状态之前：

1. **确定**：哪条命令能证明这个说法？
2. **运行**：完整运行，不用旧结果、不用部分结果。
3. **读取**：读完整输出，看退出码和失败数。
4. **核对**：输出是否支持这个说法？不支持就如实说实际状态并附证据；支持才可以声明，并附证据。

跳过任何一步，都不是验证。

## 说法 → 所需证据（本仓）

| 说法 | 需要 | 不够 |
| --- | --- | --- |
| 类型检查通过 | `pnpm run typecheck` 退出码 0 | lint 通过、"看起来没问题" |
| lint 干净 | `pnpm run lint` 零错误 | 只检查了部分文件 |
| 测试通过 | 对应 vitest 命令零失败，并读过输出 | 上一次跑的结果、"应该会过" |
| 规则门禁通过 | 对应 `verify:*` 退出码 0 | `verify:rules` 被既有 `verify:arch` 阻断后当作通过 |
| Bug 已修复 | 原症状的复现命令现在通过 | 改了代码就假定修好 |
| 回归测试有效 | 红绿都见过：撤掉修复应失败，恢复后通过 | 只跑过一次且是绿的 |
| 方案已完成 | 对照 `notes/plan-*` 验证计划逐项核对 | 测试绿了就说阶段完成 |
| 子 agent 报告成功 | 自己看 `git diff` 与验证输出 | 直接转述子 agent 的结论 |

## 红线信号

出现以下任一，停下来先去验证：

- 用了"应该""大概""看起来""好像"；
- 还没验证就表达满意（"搞定了""完美"）；
- 准备汇报完成、交接或让用户提交，但上一条验证已不是当前代码状态；
- 想着"就这一次""只是小改动""累了先这样"。

## 与其他技能的关系

- 不确定该跑哪些命令、怎么归类既有失败：用 `appworks-verify-change` 选择并归类。
- 验证失败时如实报告失败数和原因，不要缩小声明范围去适配结果。
- 本规则只管"声明前要有证据"，不授权 commit、push 或扩大改动。
