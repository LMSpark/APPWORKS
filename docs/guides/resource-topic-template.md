# 数据资源专题通用模板

每个专题按 **原理 → 方案设计 → 数据维护** 组织。设计配置与业务数据分离，全部逻辑经数据空间承载。本文规定可重复的开发与验收结构，不要求先构建新框架。

各专题都须填写下列交付合同，并将结论指向实际源码和验证证据：

| 层次 | 输入 | 输出 | 验收重点 |
| --- | --- | --- | --- |
| 原理 | 原业务用例、正式模型、资源和接口 | 业务语义、字段及标题表、输入输出与完整链路 | 事实、缺陷和待核实项分清；下游消费可追溯 |
| 方案设计 | 资源身份、设计参数 | 已保存的方案及身份 | 独立设计页；配置保存、重开、变更影响与取消 |
| 数据维护 | 已保存方案身份、业务参数 | 查询/调用结果；支持写入时另有保存回执 | 独立数据页；消费已保存方案，按资源能力查询或维护数据，不改方案 |

字段表统一记录“稳定名称、标题及其来源、值类型、归属模型、用途、校验、存储位置”。每项操作统一记录“前置条件、输入、读写范围、可见输出、持久结果、下游消费者、失败/取消后的状态”。通用模板统一开发过程；各资源的实际能力仍按自身合同核定。

## 1. 原理

先从参考业务、源码和正式模型核实：

| 项目 | 必须说明 |
| --- | --- |
| 业务目的 | 用途、使用流程、结果的下游消费者 |
| 资源结构 | 身份、字段名称、类型、标题来源、归属、输入参数、输出及层次 |
| 配置与数据 | 哪些是设计定义，哪些是用户数据，各自DataTable/DataView、存储适配及提交范围 |
| 数据空间 | DataTable如何表达定义和数据，DataView怎样查询/编辑/输出，值级联怎样配置 |
| 执行链 | 标准组件绑定 → DataView/DataSet API → 数据层资源适配 → 资源 → 结果和当次数据权限 |
| 异常与变更 | 默认值、校验、删除完整性、取消、失权、失效、部分成功、未知回执及设计变更的影响 |

字段必须说明稳定名称、类型、标题来源及用途；不能因标题为空裁剪正式结构。原代码与存量数据都可能有缺陷，分别记录已证事实、目标要求和待核实项。

## 2. 方案设计

程序员使用独立设计页，输入资源身份与设计参数，维护结构、字段标题、映射/查询规则、视图、关系和级联。设计本身也是业务：元模型由DataTable表达，标准组件绑定其DataView。输出是已保存的正式方案及身份，不夹带业务条目编辑。

配置可能存于数据库或场景文件，均作为语义资源接入DataTable；标准组件通过DataView编辑，DataSet提交捕获的变更。原文件owner只在数据层资源适配内部执行存储，不向页面提供另一套查询、暂存、取消或保存入口。未加载、未修改的内容保留，各来源分别确认结果，不承诺跨来源事务。类型或结构变更须核验对既有数据的影响，资源删除按命令语义核引用；普通保存不核全目录。取消调用原DataView的discardPendingChanges，未知回执沿同一保存链核验。

## 3. 数据维护

用户使用独立数据页，输入已保存的资源/方案身份及业务参数。页面按方案生成或配置标准字段子组件，标题、类型与规则来自已保存定义。通过完整dataViewKey绑定DataView，查询、分页、级联、编辑覆盖、权限和保存复用spark-data。

先声明本资源实际支持的操作：查询、调用、新增、修改、删除分别以正式接口与数据权限为依据。只读资源验证查询和下游消费；可写资源还须验证保存回执与新实例回读。外部接口调用须核真实业务副作用，不能仅凭请求方法判定只读，也不能给返回结果补造本地CRUD。

输出是业务数据及相应操作结果，提交范围不含设计配置。数据页可以读取配置决定呈现和校验，但不提供同屏设计编辑，不将设计草稿当正式方案，也不通过一次“全部保存”同时提交配置和数据。取消数据草稿不修改方案；不支持的操作明确记为“不适用＋合同依据”，不能用空按钮或假成功填满模板。

“程序员/用户”表示工作职责，不是前端权限角色。两类界面均消费服务端当次数据权限。

## 4. 通用实施与验收

1. 核实原理与存储合同，把输入输出策划到DataTable。
2. 查ClassModel目录、概要和指南，再编排独立设计页、数据页；组件不足先扩展标准组件。
3. 按消费需要创建命名DataView及显式级联，不另造页面查询、权限或草稿真源。
4. 验证设计保存/重开、数据页消费已保存方案、正式查询/调用结果及下游使用；支持数据写入时，再验证保存/新实例回读。
5. 验证数据操作不改设计、设计保存不夹带业务数据；存在两类草稿时不得一并提交。
6. 核取消、失权、目标切换、未知回执、旧数据兼容与资源特有异常；声明变更后正式编译ClassModel。
7. 在唯一台账记录输入输出、改动、证据和未闭合段，不另起专题总计划。

### 专题交付表（直接套用）

每个专题在既有产品文档中填写下表，实施进度仍只记入唯一台账对应编号。原理、方案设计、数据维护依次衔接；“原理”是业务与技术依据，不要求额外建一个配置页面。未核实内容填写“待核实＋依据缺口”，不能写成已实现。

| 原理 | 本专题填写内容 |
| --- | --- |
| 业务目的与用例 | 解决什么问题；调用方输入什么，结果由谁使用 |
| 资源与事实来源 | 原页面/源码入口、正式资源身份、查询及写入能力、已知缺陷 |
| 字段合同 | 稳定字段名、标题及来源、类型、所属DataTable、用途、校验、存储位置 |
| 数据链路 | 参数 → DataTable及DataView → 正式资源 → 输出结构 → 下游消费；分别标出配置和数据 |

| 方案设计 | 本专题填写内容 |
| --- | --- |
| 独立设计入口 | 原目录/导航入口、目标身份及URL参数、设计页消费的元数据空间 |
| 可维护配置 | 字段标题、类型、映射、规则、命名视图、模型关系与显式值级联；按实际能力填写 |
| 配置持久化 | 数据库/场景文件各存什么、对应DataTable资源适配、DataSet保存回执及独立重开 |
| 设计变更影响 | 既有数据、已保存模型与下游页面怎样处理；取消和不确定保存结果如何恢复 |

| 数据维护 | 本专题填写内容 |
| --- | --- |
| 独立数据入口 | 已保存方案身份和业务参数；缺少、重复、失效身份如何处理 |
| 呈现与绑定 | 标准组件、完整dataViewKey、数据成员和字段；标题/类型/规则从何处读取 |
| 业务操作 | 每项的前置条件、输入、读写范围、输出、权限、保存回执与后续消费者 |
| 结果与恢复 | 新实例回读的数据结果；取消、失权、目标切换、部分成功和未知回执的状态 |

验收记录逐项填写“源码落点、验证方式、实际结果、证据、未闭合项”。至少连通一条 **方案保存 → 新实例消费该方案 → 数据操作 → 结果回读 → 下游使用** 的用例，并分别证明配置和数据的提交范围。只读资源的数据操作按其真实查询/输出合同验收，不补造写接口。设计定义、接口响应、页面显示与测试夹具分别标明，不能互相替代验收。

专题完成以这条业务链闭合为准，不以三段文档填满或三个页面建成计数。原理是实现依据；方案设计和数据维护是两个独立工作界面，均通过同一数据空间体系承载。统一模板不要求每类资源拥有相同按钮、输出结构或持久化方式。

## 5. 字典样板

| 层次 | 实现与边界 |
| --- | --- |
| 原理 | DictionarySchema：val/txt加四个exVal输出；六项标题来自val/txt/secondValue/thirdValue/fourthvalue/fiveValue；val输出类型消费已保存且可读的编码方案，其他业务输出保持文本 |
| 方案设计 | 原路径目录及dictionary-setting，只维护名称、类型、标题等定义；saveDesign只提交定义，资源删除独立核完整性 |
| 数据维护 | 独立dictionary-data-page，URL传dictionaryId；按已保存标题显示六字段，saveData只提交条目 |
| 公共承载 | 已有字典场景的DataSet、两个正式模型及DataView；DictionaryWorkspace组织领域约束，标准组件直接绑定 |

样板验收使用实际Vue、标准组件、PageRuntime及正式查询/保存owner，只在装配入口及HTTP边界提供夹具。用例见[独立页面流程](../../tests/runtime/page/dictionary/dictionary-workflow.test.ts)与[领域约束](../../packages/spark-lowcode-api/src/platform/resources/dictionary/dictionary-workspace.test.ts)：设计标题保存后由新数据页消费、两个提交范围隔离、新建先设计后数据、取消、权限、参数/目标切换与未知回执。HTTP夹具结果不等于线上写入验收；当前证据及未闭合项仍以唯一台账为准。

数据维护还须验证辅助字段的实际写入与重开，例如字典ordIdx的排序、显式零值、取消和无写权限。生命周期区分装配在途、查询在途和保存在途，分别核失效结果与实例释放；不能拿其中一类用例代替全部。缓存页签须验证不同方案身份的草稿与取消互不覆盖。

下游消费另由[来源策划与查询用例](../../tests/runtime/auth-nav/data-space/model-source/lowcode-data-space-model-source-reader.test.ts)连接已保存设计、模型字段、DataSet装配与正式DataView查询，验证六字段输出、数值/字符类型及选择值兼容。设计变更不自动改写已保存业务模型；每个专题都须明确这类影响边界，不能以维护页保存成功代替下游验收。

外部API、逻辑视图沿同一模板分别核资源特性。外部API不自动等于可写本地表，逻辑视图不自动支持主从写入；不能为了统一按钮而伪造CRUD能力。

外部API的当前应用示例：原理沿服务商、公共参数、头部取值函数和后端执行链核对；方案设计在原路径维护基础定义、公共参数、头部和令牌前缀，各自限定保存视图；账号值和真实调用属于独立数据维护链，仍待实施。标准值函数字段通过完整视图键消费已保存参数候选，不执行请求。该例已验证局部方案保存和新实例回读，但不满足完整专题的“数据操作→下游使用”验收，不把方案设计完成冒充专题完成。当前产品事实见[外部API合同](../architecture/DATAFLOW_ARCHITECTURE.md)。
