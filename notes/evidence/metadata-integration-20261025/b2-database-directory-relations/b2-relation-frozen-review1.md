## Spec and quality review

**No blocking implementation finding in the reviewed scope.** The implementation now follows the selected `Base_TblRln@forTable` DataView as the sole record/overlay owner. `database-catalog-relation-form-ops.ts:13-24,91-128` defines the nine real editable fields and session/checkpoint identity. Create requires `commitMode === 'staged'`; edit derives role from the existing overlay, rejects a row that does not uniquely touch the current table, and checkpoints only those nine fields. Cancel restores the checkpoint for edit and discards only the staged new row. `table-relation-dialog.vue:10-18,27-29` binds `rlname`, the peer endpoint, cascade, and `RelshipExp` to standard fields on the same DataView; no page draft or hand-built peer options array remains.

- **Role/peer atomicity and permissions:** role switching preflights every endpoint field plus `RelshipExp` before writing any values, retains the opposite endpoint only when it is a different table, clears the old expression, and leaves `rlname` alone (`database-catalog-relation-form-ops.ts:144-166`). Peer changes verify the actual loaded peer row belongs to the current DB, differs from the selected table, and has nonblank id/name; all target fields are checked before any overlay update (`:169-190`). Tests cover denied last-field role switch and denied later peer field leaving the overlay unchanged (`table-and-view-page.test.ts:1472-1523`).
- **Formal endpoint/field validation:** structural changes and staged creates validate two distinct complete endpoints against the exact `relationEndpoints` view and matching DB/name identities; then query physical `Base_TblField` rows by endpoint ids, require complete readable rows, and validate existing expression field references (`table-and-view-page.test.ts:934-1011`). The two query boundaries recheck captured DataSet/view/session/table selection and an overlay snapshot before accepting results. Loading, unreadable field, missing/duplicate endpoint, and late overlay change cases keep the pending overlay and send no write (`tests/runtime/page/database/table-and-view-page.test.ts:1621-1748`). Name-only edits intentionally bypass historical structural repair, but a snapshot check prevents structure added during its asynchronous boundary from being submitted; the cross-database legacy test confirms only the name remains staged and no request is issued (`:1754-1779`). This matches the principal ruling; it does not globally repair untouched legacy expressions.
- **Unknown writes and scope:** the page skips ordinary structure preflight when the original view has an unconfirmed save and checks captured query/session identity before calling `DataSet.saveChanges` with only the requested relation row (`table-and-view-page.vue:1117-1150`). The unknown integration case establishes an accepted-then-lost receipt, keeps the dialog/cancel lock, resolves via the captured DataSet save path, and asserts no second CRUD POST (`table-and-view-page.test.ts:1782-1823`). The owner-level test also verifies only the requested row is submitted and that JSON payloads retain their shape (`:1920-1979`). The page's dirty source reads all DataSet views, including pending and unknown state (`:1481-1489`), so this protection does not depend on a one-off component event.
- **Late results/close protection:** the tested late-query case switches the selected table while a previous relation query is held; only the replacement table's relation rows remain after the older response completes (`table-and-view-page.test.ts:1982-2010+`). Dialog close is disabled while busy or unknown (`table-relation-dialog.vue:6-7,66`); the page registers the dirty source from actual DataSet view state, and standard expression editing sets the existing dirty-source flag, with a system-page close test covering an uncommitted expression candidate (`table-and-view-page.test.ts:1329+`, `table-and-view-page.vue:908-910,1481-1489`). Forced runtime teardown remains the previously established host boundary, not changed by this round.
- **Mixed DataType:** formal type mapping uses `DataType` (`table-and-view-page.vue:1150-1159`), not display `DataTypeName`. Unknown-type child fields are omitted from typed candidates while a warning is shown; the standard expression renderer remains available when the stored expression uses a mapped field (`:1267-1293`, `table-relation-dialog.vue:20-30`). If the stored expression actually references an unmapped child type, it is identified as unsafe and editing is blocked without changing the stored overlay (`expressionReferenceError` at `table-and-view-page.vue:1180-1213`; test `table-and-view-page.test.ts:1308-1327`).
