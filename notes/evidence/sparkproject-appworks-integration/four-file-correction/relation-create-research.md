## 可收敛的新增流程

1. 新增按钮与有效 connect 事件走同一独立创建命令。表单先收集父/子候选的正式 rowid、正式字典 `depType`、结构化 Filter 的原始序列化值，以及可选 Join 三项。connect 仅预填两个端点；手动新增无默认端点。原表单的空 `depType`、空过滤器及子模型既存 Join 是源事实，**不能把子模型现有 Join 默认为这条新关系可改**。新增 `cascadeDel` 按 brief 的源常量 `0`；正式关系 `rowid` 交 `DataView.addRow`/原查询 owner 分配，不由图临时 ID 冒充。
2. 独立输入只使用当前正式可读模型候选：目标 `dataSetId` 与当前空间一致，`rowid` 和非空 `Name` 可读，Name 身份唯一；无权、隐藏、脱敏的名称不暴露。`depType` 须来自已读取的正式字典且显式选择；子模型外键仅从可读正式字段 Name 选择；Join 三项全空或全填，非空 PId 是所选父正式 Name。已有其他父 PId 时显示归属并拒改那四项，同时允许不修改 Join 的关系新增。Filter/JoinFilter 使用控件对当前 contextKey 和原值的 validation 报告；空表达式是否有效沿控件正式报告，不另写解析器或默认选第一项。
3. 打开与提交前均核当前快照/目标、`designRelations.addActionState()==='enabled'` 和模型/字典/字段候选仍在本次正式查询内。不存在的新行没有 `fieldAccess` 合同；`allowAdd` 也不产生字段写权限。已存子模型 Join 真实变更仍按它的 `fieldAccess`、编辑动作状态和独立脏状态逐字段核。优先研究让 `designRelations.addRow` 创建的 pending-create 行成为唯一创建草稿：独立有限输入 UI 可调用 `editRowById`/`updateEditingValue` 更新它，每次核新增动作与 owner，而不调用 pending 行的 `fieldAccess`；原查询 owner 在正式保存时回放新增凭据。取消该 ID 仅 `discardPendingChanges([newId])`、零 HTTP，不能清别人的编辑。删除尚未提交的创建行等同取消。若决定等完整输入才 addRow，则此前非空输入另需跨 Renderer 草稿 owner，不能藏在脚本变量。
4. 提交复用现有 `designSaveRelation` 的同一 `designDataSet.saveChanges({views:[...]})`，只列实际改变的 `Base_DataModel/designModels/childId` 与 `Base_DataModel_Relation/designRelations/newId`。先核全部业务输入与模型字段，后 stage，核 tableName/viewId/动作/计数回执，再以同一目标正式全量回读并按 rowid/空间/字段逐项确认；关系与 Join 无同一事务保证。其他 pending/editing row 不混入也不清掉。`parentTable/childTable` 取可读正式 Name，过滤式保持原序列化值。
5. 元数据已确认后才走现有 `designPersistRelationLayoutEdge({action:'add',id:newId,...})` 的内容 owner：保留原图节点、边几何和扩展属性；相同端点的不同 ID 应分别有边。布局文件缺失、原文变化、草稿/在途/未知或图写失败须报告“关系元数据已确认，布局未确认”，禁止自动覆盖或重发关系保存。现有函数在布局有两端节点时按新 ID 加边；布局无节点时不写文件，需明确提示不能把图可见误报成功。图 connect 本身不能生成持久关系或污染布局草稿。

## 生命周期与异常边界

- `DataView.addRow` 在 staged 模式追踪 pending-create；`editRowById` 只核当前查询 owner/过期状态，更新行并调用 `markDirty`，**不调用**新行 `fieldAccess`；`DirtyTrackingDelegate.markDirty` 对 pending-create 明确忽略，所以指定行仍只会作为 add 提交，不会同时成为 change。`PageRuntime.isDirty` 已遍历 pending/editing，因而 pending 行能保护关闭/刷新/切换。可是本页当前 `designVerifyRows` 要求 `rows.length===view.total` 且每行身份字段 `fieldAccess(...).read==='visible'`；`addRow` 只 append rows，不增 `total`，新行也没有正式行权限。直接 addRow 会使 `designEntryIsCurrent/designSnapshotIsCurrent` 失效。现有 `designRelationUpdateSnapshotAfterOwnedMutation` 只替换 rows/total 引用，不解决验证器；必须将正式查询基线行与**明确由本次 owner 追踪的一个 pending-create ID** 分开核，不能把所有无权限行当草稿或绕过原正式行校验。图解析也只能把 pending 行视为未提交关系，不得要求原图已有其边。此为本页快照接线，优先于新增通用 API。
- `__init__` 目前只识别输入参数 DataView 的 pending/editing；关系 pending 时它走 `designReloadDesignCore(true)`，后者加载服务器，`DataView.assertResultReplacementAllowed` 会因未保存变更拒绝替换。要让 DataView 草稿跨同一 PageRuntime 的 Renderer 重挂载，需在 `__init__` 先识别 `designRelations` 的那个 pending ID，沿 `designRebuildFromCurrentViews` 一类本地快照重建而非远端覆写，恢复创建 UI、Filter context 与真实 owner 身份；本地重建同样要区分正式/待新增行。其他关系更新/删除草稿、模型 Join 草稿不能被误认作此创建命令。若创建动作在用户未选端点前已有非空输入，而尚不能安全 addRow，`PageRuntime.getContent(key)` 的 opaque text 草稿/`onContentChange` 是已存在的最窄候选，需经受限 PageContext 桥接；当前仅布局专用桥，不能声称已可用。应先明确何时入行，争取让 pending 行从创建流程可编辑起就承载唯一草稿，不共用布局 key或新造框架。
- **保存时序已读穿，纯 pending-create 不足以完成关系新增闭环。** `DataSet.saveChanges` (`packages/spark-data/src/dataset.ts:1332-1415`) 收集指定视图后调用 `DataView.saveQueryViews`；后者 (`data-view.ts:2020-2063`) 在 DataView 上设置 `mutating`，直接 `await executor.save`，没有传 Renderer 的 AbortSignal。请求 promise 由 DataSet/DataView 持有，旧 Renderer abort 不取消它。唯一 owner 在全部模型回执通过校验后调用 `acceptQuerySaveReceipt`；该方法先把 `#queryResult` 换为回执新 context，再对新增 `cancelCreate(submitted.id)`、以服务端行替换本地行、更新 total 并发 `rowsChanged` (`data-view.ts:2109-2171`)。`finally` 清 `mutating` 并发 `mutatingChanged`；新 Renderer 的 `ds.onAnyViewChange` 已订阅这两个事件（`SparkPageRenderer.vue:217-230`），所以能刷新行/请求状态，但事件**没有关系闭环阶段、待回读目标与布局待同步命令**。
- 旧脚本的 `designSaveRelation` 在 `await dataSet.saveChanges` **之后**才检查自身 capture、正式 `loadFromServer` 逐目标回读、执行 `designPersistRelationLayoutEdge` 和重建快照。旧 Renderer 释放时 `buildPageContext` 的旧 `$page` 已因 abort 失效；即使 DataSet 后台接纳回执，旧脚本不能可靠完成这些后续步骤。此时 pending-create 已清，若无其他草稿，`PageRuntime.isDirty` 只看 DataView pending/editing 和 runtime content，可能为 false；新 Renderer 会读到正式关系，却不知同一 ID/Join 候选是否已精确核验，也不知布局是否须后置同步。`designParseLayout` 只要求现存图边能匹配正式关系，不要求所有关系都有边，故旧图缺新边不必然报错。纯 DataView pending 路线只能覆盖**提交前草稿和请求未接纳期间**，不能覆盖回执接纳到回读/布局结束的空窗。`mutating` 也不进入 `PageRuntime.isDirty`，不能独自作离页锁。
- 最窄必要补充是复用现有 `PageRuntime.getContent(key)` 的**命名不透明文本**与 `onContentChange`：本页为当前目标和新关系 ID 在提交前存一条可恢复流程记录，内容仅含精确 ID、端点、拟提交关系/Join 候选与阶段（发出前、结果待核、元数据已核/布局待核），不把关系 I/O、权限或解析搬进 `project-model`/`buildPageContext`。该 key 首次以 `acceptRead('')` 建立本地空基线（**不读取远端文件**），再用 `setDraft` 写记录；`draft` 非空使 runtime 在保存/回读/布局期间保持脏，确认完成时 `discardDraft`。旧 Renderer abort 后记录仍在同一 runtime，新 Renderer 可从当前 DataView 的 pending/mutating、记录及正式按 ID 回读推导下一步。DataSet 仍唯一发送 `saveChanges`，新 Renderer 遇“结果待核”**只读核对，不重复 create**；元数据回读确认后按现有布局 owner 的预像/状态决定是否只同步边。仅当两段结果均确认才清记录；失败/不一致保留记录并明确人工核验。已有 `PageContentRuntime.startWrite` 绑定文本预像并自动把 submitted 视为写入成功，不适合包裹多视图保存/关系算法，**本建议只用其文本草稿/通知能力**。PageContext 只需受限的命名记录读/写/丢弃桥，不暴露任意 runtime content 给页面或新增 HTTP 通道。
- 请求发出前的校验/入行失败可丢弃**本命令** pending row 并保留可修正输入；请求发出后失败、回执不符、回读失败或目标/查询切换为结果未知，锁重复提交，按正式关系 ID 和子模型 Join 精确重读核对。取消本地表单不撤销已发送请求；显式重读前不得清未知。元数据已成功、布局未确认应保留独立部分成功状态，后续只核对/修复图，不再调用关系 create。原页曾只靠卸载清表单与 `verificationError` 锁，这是源事实，不等于本仓安全生命周期。

## 准确接线范围与待核合同

- 页面最窄现有文件：`config/pages/data-platform/data-space-design/{rule.json,script.js,style.css}` 与 `tests/runtime/page/design/data-space-design-four-file.test.ts`；复用既有 `pagedata.json` 命名视图，除非正式绑定字段证据要求变更。`DataSpaceDesignGraph.vue` connect 事件已够两个端点；不需修改图组件或建图几何算法。现有 Filter/Join 控件与正式依赖字典入口可直接消费，不重写表达式/字典。
- 本页须处理 `designVerifyRows/designEntryIsCurrent/designSnapshotIsCurrent/designRelationUpdateSnapshotAfterOwnedMutation/__init__/designRebuildFromCurrentViews` 的 pending-create 识别与恢复。保存回执到布局完成的空窗已证实，故仍需一个由既有 `PageRuntime.getContent/onContentChange` 承载的命名不透明**流程记录**及到 PageContext/脚本类型的受限读/写/丢弃桥；对应 runtime/Renderer 测试需证明旧 Renderer 失效后新实例获知 DataView 后台结算，恢复为“按 ID 只读核验/布局同步”，不重发新增。该桥不实现关系保存，也不修改 Pool/导航/新框架。若入行前允许用户填写非空输入，可用同一记录临时承载，再在 pending 行建立后转交 DataView；优先让 pending 行从可编辑起即为唯一业务草稿，避免重复值源。
- 尚缺的明确合同：独立输入在未选端点/已选端点时的 UI 呈现及关闭动作；输入草稿与同页既有关系编辑能否并存（建议互斥，避免另一个 editor 抢 `currentRow`）；同端点多条关系在图上的重叠选择方式及点击后按边 ID 定位；关系元数据保存中旧 Renderer 释放后的 DataSet 回执/脏状态；布局部分成功跨重挂载时的可见恢复入口。这些不是允许按端点合并、借旧行字段权限或自动重试的理由。
